# Decisions

This library's guideline decisions, recorded on 2026-11-21 (Epic #5, Issue #2). Each one is
written in the Fragiola guidelines (`../guidelines`, paths below relative to it), and this page
mirrors them. The maintainer's decisions D1–D10 are in [`handoff.md`](handoff.md); they are not
repeated here.

| topic | decision | guideline page |
| --- | --- | --- |
| Library pattern | Core + adapters is the default. This library is the second pattern, **native primitives**: a spec per component, the framework-free DOM toolkit, one native implementation per framework, a styling layer for examples and tests, one conformance suite. No model API, no command bus, no stateful core (D3). | `architecture/native-primitives.md`, `decisions.md#library-pattern` |
| Part attribute | `data-primitives-part="<component>-<part>"` on every element (`"dialog-popup"`, `"menu-item"`, `"tabs-tab"`). State stays Base UI-style (`data-open`, `data-highlighted`, `data-popup-open`, ...) under the boolean rules: present or absent, never `"false"`. The POC's `data-<component>-part` is converted during the port. | `components/primitives.md#the-primitive-contract`, `decisions.md#np-part-attribute` |
| Toolkit re-export | The framework packages **do not** `export *` the toolkit (it would defeat D8). A toolkit type that appears in a component's API (`PlainDate`, `Side`, `Align`) is re-exported as a type from that component's entry. The toolkit is a regular `dependency`, published as the exact version. | `architecture/native-primitives.md#the-toolkit-boundary`, `decisions.md#np-toolkit-re-export` |
| Entries | One entry per component in every framework package, one per mechanism in the toolkit, and a root entry that only re-exports. tsdown multi-entry `exports` for the toolkit, React and Vue; one ng-packagr secondary entry point per component in Angular (as `../tree/packages/angular` does for features). Global providers (direction, locale) in their own entries. `check:package` checks every subpath. | `architecture/native-primitives.md#tree-shaking-a-hard-requirement`, `decisions.md#np-entries` |
| Source layout | Per-component folders inside the responsibility folders (`components/dialog/dialog-popup.tsx`) satisfy `repository.md#source-layout`. The toolkit has one folder per mechanism. Angular: each component's code lives in its ng-packagr secondary entry point's folder, organized like a `src/` (`packages/angular/dialog/directives/dialog-popup.directive.ts`, `dialog/inject/`), and the code the entries share in the `internal` entry (`packages/angular/internal/utils/`): ng-packagr compiles an entry point from its own folder (a file outside it fails with TS6059, `rootDir`), as Tree's feature entries do; `src/` holds only the root entry, which re-exports the components' entries (amended during Issue #3). | `architecture/native-primitives.md#source-layout`, `decisions.md#np-source-layout` |
| Tests | `conformance/` is the per-component referee: behaviour (with axe), contract and visual layers over the `fixtures/<framework>` apps, with one golden set made by React in CI. `examples/shared` holds the site examples' shared Playwright specs. No `apps/playground`. | `architecture/native-primitives.md#tests`, `decisions.md#np-tests` |
| Examples styling | Fragiola UI is Base UI + React, so it styles neither the Vue and Angular examples nor these primitives' examples. The examples and fixtures use the POC's recipes (Tailwind v4, keyed on `data-*`) on Fragiola UI's palette roles, with the five example themes (`light`, `dark`, `ide`, `paper`, `terminal`, shape tokens included). | `architecture/native-primitives.md#examples-styling`, `decisions.md#np-examples-styling` |
| Vue and Angular idioms | As the API mapping table of `spec/README.md`, cross-checked with `../tree` and `../splitter`. Vue: `as` or the `render` scoped slot, `class` / `style` values (state through `data-*` or the slot), template refs (`$el`), `v-model:<prop>`. Angular: attribute directives on the consumer's element, `state()` through `exportAs`, template reference variables, two-way `[(prop)]` bindings (an input with its `*Change` output, the shape of a `model()` input; the input plus output is used where a one-way binding must stay controlled). | `components/primitives.md#in-vue-and-angular`, `decisions.md#np-idioms` |
| Bundle guard | Per framework, a fixture app importing two components (Dialog and Tabs). It fails when any other component's code or an unused toolkit mechanism is in the output, by markers or source maps. Run by `pnpm build` and in CI; a test plants an import and sees it fail. | `architecture/native-primitives.md#tree-shaking-a-hard-requirement`, `architecture/features.md#guarantees-to-enforce`, `decisions.md#np-bundle-guard` |
| Modal overlays in the embeds | Each framework's embed host ports `../ui/examples/react/src/host/overlay-promotion.ts` (CONTRACT §5.4). The copyable example files never know about it. | `docs/site.md#examples`, `decisions.md#np-modal-overlays` |
| Site IA | "API: core (model, commands)" becomes "API: DOM toolkit (`@fragiola/primitives`)", plus one page per component: behaviour summary with the APG pattern, anatomy, per-framework usage, props, state and part attributes. Concepts: the pattern, the primitive contract, state and part attributes, tree-shaking, the behaviour rule (D4). | `docs/site.md#a-native-primitives-library`, `decisions.md#np-site-ia` |
| Runtime dependency | The toolkit keeps the POC's single runtime dependency, `@floating-ui/dom`, in the positioning entry only: the recorded exception to "zero runtime deps". | `architecture/native-primitives.md#the-toolkit-boundary`, `decisions.md#np-runtime-dependency` |
| Site contract | Target `../www/CONTRACT.md` v1.7 (`CONTRACT_VERSION` `"1.7"`), the current version. The dev port is 5191 (`site:dev`); the library is not in `../www/projects.json` until the maintainer validates it. | `docs/site.md#what-a-new-library-provides`, `decisions.md#np-contract-version` |

## Overlays: details decided during Epic #7 (Issue #6)

Questions the handoff §3, the APG and Base UI did not settle, decided by the Epic's stop condition
(take the APG-closest option, record it in the spec and here).

| topic | decision | alternatives discarded | spec |
| --- | --- | --- | --- |
| How "unless the press landed on a focusable element" is checked | The toolkit's overlay session waits until the outside press has ended (pointerup, then a task, for touch), then returns focus only when focus is on the body: whatever the press focused, it keeps (`returnFocus.whenUnfocused`). A press inside a dialog's popup (`tabindex="-1"`) therefore keeps focus on that popup | testing the press target for focusability at pointerdown (misses a focusable ancestor and the browser's own focus rules) | `popover.md` "Focus", `dialog.md` `/dialog/nested-popover` |
| The focus an outside press gives | Not reported again as `focus-out`: the press already dismissed the overlay with `outside-press` | reporting both reasons | `popover.md` "Focus" |
| `data-side` of a flipped side | Named as it was asked: a flipped `inline-end` reports `inline-start`, a flipped `right` reports `left` (Base UI) | always logical, or always physical | `popover.md` "Positioning", `README.md` |
| How a modal menu blocks the outside pointer | The body stops taking pointer events (`@fragiola/primitives/inert`, `blockOutsidePointer`) and the trigger and every level's positioner take them back (`pointer-events: auto`, structural inline style): no extra backdrop element in the DOM | an invisible backdrop part (one more element in every framework's DOM and the goldens); capture listeners that cancel events (they cannot stop hover) | `menu.md` "Modal" |
| A modal menu's outside press and focus | It closes every level and focus returns to the trigger (the press reaches nothing to focus); the keyboard is unchanged (no trap, no inert page: Tab still closes and moves on) | trapping focus like a dialog (the APG menu has no trap) | `menu.md` "Modal", "Focus" |
| A submenu and `modal` | A submenu follows its root menu; `SubmenuRoot` takes no `modal` (Angular's shared `MenuRoot` directive accepts the input and ignores it on a submenu) | a per-level option | `menu.md` "API" |
| A non-modal menu's outside press | Unchanged from the POC: no focus return, the press reaches the page | returning focus like the Popover (not in §3) | `menu.md` "Focus" |

## Forms and selection: details decided during Epic #9 (Issue #8)

Questions the handoff §3, the APG and Base UI did not settle, decided by the Epic's stop condition
(take the APG-closest option, record it in the spec and here).

| topic | decision | alternatives discarded | spec |
| --- | --- | --- | --- |
| Select typing while closed, with no match | Nothing happens: the list stays closed (the POC's behaviour) | opening on the selected or first item | `select.md` "Typing while closed" |
| Select typing while closed, on a disabled item | The disabled item is highlighted (options stay discoverable), never chosen | skipping disabled items | `select.md` "Typing while closed" |
| A modal Select's outside press and focus | The press reaches nothing and would leave focus on the body, so focus goes back to the trigger (`returnFocus.whenUnfocused`, as Menu's modal) | leaving focus on the body | `select.md` "Modal" |
| How a modal Select blocks the outside pointer | As Menu's: the body stops taking pointer events, the trigger and the positioner take them back; the lock and the block have their own effect, so toggling `modal` while open keeps the session | an invisible backdrop part | `select.md` "Modal" |
| A highlighted option scrolled into view | Only inside its popup (`@fragiola/primitives/collection`, `scrollIntoViewWithin`): `Element.scrollIntoView` also scrolled the page when a list mounted before it was positioned at the end of a tall page | `scrollIntoView` with `block: "nearest"` (the POC) | `select.md`, `combobox.md` |
| CheckboxGroup's API | One component (`CheckboxGroup`, Angular `[checkboxGroup]`), as Base UI and the POC; its own entry `/checkbox-group`; its example is the Checkbox example (Pizza toppings) | a `CheckboxGroup.Root` namespace | `checkbox.md` |
| Field's binding in Angular | In the `field` entry, exported as the lower layer (`injectField`, `fieldControl`, `writeFieldAria`); Checkbox, Select, Slider and Combobox import `@fragiola/primitives-angular/field`. `/internal` cannot hold it: it would import the field entry, which imports `/internal` | `/internal` | `field.md` "Integration contract" |
| Field's scope | The POC's Field, ported as it is; production scope (Fieldset, Form, async validation, ...) is stage 1 | extending it now | `field.md` |
| Combobox's part on triggers | `data-popup-open` on the Input, InputGroup and Trigger (Base UI's names, D4 §3 "Naming"); `data-open` stays the Positioner's and the Popup's | `data-open` (the POC) | `combobox.md` |

## Dates: details decided during Epic #11 (Issue #10)

Questions the handoff §3, the APG and Base UI did not settle (Base UI has no calendar), decided by
the Epic's stop condition (take the APG-closest option, record it in the spec and here).

| topic | decision | alternatives discarded | spec |
| --- | --- | --- | --- |
| Entries | One per component, `/calendar`, `/range-calendar`, `/date-picker`, `/date-range-picker`, over shared modules: RangeCalendar's Root and the Calendar's parts, DateRangePicker's Root and the DatePicker's parts. The bundle guard keeps all four and `/date` out of the Dialog + Tabs app; a Calendar alone never imports a picker's module (the binding the pickers provide lives with the calendar) | one `/calendar` entry exporting Calendar and RangeCalendar (and one `/date-picker` for both pickers) | `calendar.md` "Anatomy" |
| The part attribute of shared parts | Named by the root they sit in: `calendar-cell` in a Calendar, `range-calendar-cell` in a RangeCalendar, `date-picker-*` / `date-range-picker-*` (the root's component, read from its context) | `calendar-*` for both (the POC's one `data-calendar-part`) | `calendar.md` "Anatomy" |
| Angular's shared directives | The Calendar's part directives (`[calendarCell]`, ...) serve both roots and `/range-calendar` exports them again (likewise the picker parts from `/date-range-picker`); the calendar and date-picker entries export their bases and tokens (`CalendarRootBase`, `CALENDAR`, `PICKER_BINDING`, `DatePickerRootBase`, `DATE_PICKER`) as the lower layer the other entries build on | `[rangeCalendarCell]` aliases | `calendar.md` "Anatomy" |
| The pickers' popup | Non-modal, as a Popover (not trapped, Tab out closes), kept from the POC; the APG example is a modal dialog with OK / Cancel | a modal picker | `calendar.md` "Differences from Base UI" |
| A picker trigger's open state | `data-popup-open` (Base UI's trigger name, D4 §3 "Naming") | `data-open` (the POC) | `calendar.md` "State attributes and ARIA" |
| A picker's outside press and focus | As Popover's (D4 §3): focus returns to the trigger unless the press focused something (`returnFocus.whenUnfocused`) | no focus move (the POC) | `calendar.md` "Focus" |
| A picker reopened during its exit animation | Its calendar, still mounted, takes the focus again (the binding carries the picker's `open`); a closing picker's calendar takes none | relying on a remount (failed when reopened quickly) | `calendar.md` `/date-picker/basic` check 4 |
| A picker reopened during its exit animation, in detail | It reseeds the focused date from the value (else today) and closing cancels a started range, as a remount would (found by the review: the focused date and a range start survived) | keeping the last navigated date | `calendar.md` "Focus" |
| A disabled calendar, a disabled date | A disabled calendar's grid has no tab stop; a press on a disabled date never focuses it (`mousedown` default prevented) | the POC's tab stop on a disabled grid | `calendar.md` "State attributes and ARIA" |
| A calendar inside a picker of the other mode | Not bound (a Calendar in a DateRangePicker keeps its own value) | binding any calendar | `calendar.md` "Anatomy" |
| The picker's popup name | No name of its own (no text); the fixtures and examples give `aria-label` | a name from the calendar's heading | `calendar.md` "API" |
| A cell's `aria-label` in Angular | A static `aria-label` of the consumer's replaces the `Intl` name (`ownAttribute`), as React's and Vue's props do | the host binding always winning (the POC) | `calendar.md` "API" |
| A form | The pickers take no `name` in stage 0; the example's hidden input carries the ISO date. Form support and Field come with stage 3 | adding `name` and a hidden input now | `calendar.md` "Purpose" |

## Hardening: details decided during Epic #22 (Issues #18–#21)

The Stage 0 follow-ups and server rendering. No rule of the handoff (D1–D10, §3, §4) changed.

| topic | decision | alternatives discarded | spec |
| --- | --- | --- | --- |
| Angular's presence | Its effect runs after rendering (`afterRenderEffect`), so the exit is awaited once the popup carries `data-ending-style`: every Angular overlay now plays its exit transition and can be reopened during it, as React's and Vue's (`conformance/tests/presence`) | a frame's wait before `waitForAnimations` (the plain `effect` ran before the view was refreshed and found no animation) | `dialog.md` "Animation" |
| Angular's Tabs Indicator | Structural, `<span *tabsIndicator>`, as its panels: not rendered while no tab is selected, as in React and Vue (`/tabs/none-selected`) | keeping the attribute directive and recording the difference (Stage 0) | `tabs.md` "API" |
| A close made through the controlled `open` | Every overlay root keeps the reason of the change that made its current `open`, `null` when the bound `open` changed with no request of its own: a close never reuses the previous reason. Popover, DatePicker and a root Menu read it as `none`, which returns focus like an outside press: only when focus was left on the body or inside the closing popup (the toolkit's `whenUnfocused` now counts focus inside the closing overlay; found by the review for Menu and DatePicker). A request the consumer turned down is forgotten once answered (a microtask) | keeping `lastReason` (it pulled or kept focus by an earlier change); always returning focus (steals focus the consumer moved) | `popover.md` "Focus" |
| Tooltip.Provider's props at runtime | One delay group for the provider's life in every framework; the toolkit's `createDelayGroup` takes a `timeout` getter read at each check, so a change keeps the open member and applies to the next hand-off | a new group per change (Angular and React: the open tooltip stayed in the old one); Vue's timeout read once | `tooltip.md` "Delay group" |
| A key on an open Menu trigger | Enter, Space and the arrows do nothing on a trigger whose menu is open, and leave no highlight pending (a later open through `open` highlighted the first item) | moving the highlight to the first item | `menu.md` "Keyboard" |
| Escape in a RangeCalendar inside an overlay | While a range is started, the grid takes Escape before the layers (`interceptEscape`, which now takes a `when` filter: only the keys pressed inside the grid): it cancels the range, and the next Escape closes the picker, dialog or popover | the layer closing first (Stage 0) | `calendar.md` "Keyboard" |
| A Vue calendar's picker binding | A computed from the current props (a `value` given later unbinds it), not decided once at setup | | `calendar.md` "Anatomy" |
| Vue Combobox callback types | `filter`, `isItemEqualToValue`, `itemToStringLabel` and `itemToStringValue` take `never` for the item (and `filter`'s `itemToString` takes `unknown`), as Angular's inputs: `ItemFilter<Country>`, `containsFilter<Country>()` and `(c: Country) => string` bind with no cast and no `any` (type tests in both packages). The public types `ComboboxFilter`, `ComboboxItemEquality`, `ComboboxItemToString` | a component generic over the item type (Vue's declared public types are not generic, and `vue-tsc`'s inference over a declared generic constructor is not reliable); `ItemFilter<unknown>` with a cast (Stage 0) | `combobox.md` "API" |
| The bundle guard between imported components | Besides the Dialog + Tabs app, every component entry of the built packages is read alone (its chunks, and the entries it imports, through their source maps), against `ENTRY_DEPENDENCIES` (the form controls on Field, Checkbox on its group's context, the pickers on the calendars) | 45 one-component guard apps (a build each: minutes on every `pnpm build`) | |
| `check-package`'s pnpm | The scratch apps declare `packageManager: pnpm@<pinned>` and run the pinned pnpm (`pnpm dlx pnpm@<pinned>` when the machine's differs), logging it; a mismatch fails | corepack (Node 25 stopped shipping it) | |
| `docs/size.md`'s gzip sizes | `size --check`: minified sizes exact, gzip sizes within 16 B or 2%, whichever is larger (Node's zlib differs between versions; a change of code always moves a minified size). The rule is in the report's header | a pure-JS deflate as a new dev dependency; dropping gzip from the check | |
| Server rendering: the layer | A fourth conformance layer, **ssr**: each fixture has a server entry (`react-dom/server`, `vue/server-renderer`, `@angular/platform-server` as the Angular fixture's dev dependency) and a `build:ssr`; `conformance/src/ssr-server.ts` serves it (in German, so a server-language fallback fails); every spec scenario is rendered, hydrated, and compared with the browser's own render (no warning, the server's ids kept, the same DOM tree) | one SSR test per component; testing in the published packages | `README.md` "Server rendering" |
| A calendar's default locale on a server | With no `locale`, the server's render and its hydration use `en-US`: React through `useSyncExternalStore`'s server snapshot (a browser-only render reads the document at once), Vue until mounted (a picker's calendar that took the focus takes it again in its new rows); Angular reads its document's `lang` on the server too and falls back to `en-US` there (never the server's language). "Today" stays read at render, documented | reading `navigator.language` at render (the server's own language); a `today` prop | `calendar.md` "API", `/calendar/single?locale=none` |
| Ids on a server | Angular's generated ids come from a root `IdCounter` (one per application, `APP_ID` in the id when it is not the default), not the toolkit's realm-wide `createId`, which a server shares between pages; React and Vue keep `useId` | Angular's `createId` (a hydrated page changed every id) | `README.md` "Server rendering" |
| Angular's hidden inputs | Inserted after the first render (`afterNextRender`), never on a server nor during a hydration (a node inserted while hydrating breaks it, NG0502); the slider's, appended at the end of its root, in a browser-only effect (after the render, its Field missed them) | rendering them on the server and adopting them on hydration | `README.md` "Server rendering" |
| Vue registrations in a server render | A Field label's id and a control's registration are cleared on unmount, not in a watch's cleanup (a server render stops the watch once the part rendered, before a later part read it); `renderPart` renders no child for no content (a void element took a comment placeholder the server never writes) | | |
| The Tabs Indicator before hydration | Rendered once the selected tab is measured (so it first appears in place), or at once with Base UI's opt-in `renderBeforeHydration` (Angular: `*tabsIndicator="true"`): the server writes an inline script inside it, the toolkit's self-contained `placeTabsIndicator`, which sets the variables as the page parses and removes itself. The Slider thumb needs none (a percentage) | an always-on script (a CSP blocking inline scripts would leave it in the DOM); CSS anchor positioning | `tabs.md`, `slider.md` "Server rendering" |
| An axe check during a transition | Every axe check (conformance and examples) waits until the page's animations have finished (`settleAnimations`), in every framework; no rule is disabled | retrying the check, disabling `color-contrast` | |

## Behaviour differences

The differences between the POC and Base UI, decided with the behaviour rule (D4: APG first,
then Base UI), are in [`handoff.md` §3](handoff.md#3-the-behaviour-differences-decided-d4-applied).
They replace the POC's own `docs/decisions.md` ("follow Base UI, with two exceptions"). A new
difference is decided the same way and written in the component's spec with its reason.
